# kernels

[![ci](https://github.com/go-videodsp/kernels/actions/workflows/ci.yml/badge.svg)](https://github.com/go-videodsp/kernels/actions/workflows/ci.yml)
[![Go Reference](https://pkg.go.dev/badge/github.com/go-videodsp/kernels.svg)](https://pkg.go.dev/github.com/go-videodsp/kernels)
[![License: BSD-3-Clause](https://img.shields.io/badge/License-BSD--3--Clause-blue.svg)](LICENSE)

Video codec kernels shared by the go-avkit decoders. Every kernel computes the
integer result of the standard's equations (ITU-T H.264 (V16) (06/2026) for
now), has a portable Go implementation written from those equations, and, where
the hardware has one, an assembly implementation. H.264 is the first consumer
(go-avkit/h264); HEVC and AV1 reuse the same packages. The design, with the
profile that sets the priorities, is in
[docs/design/design.md](docs/design/design.md).

Implementations: portable Go on every target (and with the `purego` build tag),
arm64 NEON, generated by `internal/genmc` (and `internal/genitx` for `itx`), and amd64 AVX2, generated by
`internal/genluma86`, `internal/genweight86`, `internal/genlf86`, `internal/genitx` and `internal/genchroma` (which writes both targets for `PutChroma`), selected at
start-up by `cpu.HasAVX2` (CPUID and XGETBV; the portable code runs without
AVX2 or with the `purego` tag). Samples are 8 bits; 16-bit forms are not there
yet.

How to read the FFmpeg column (method in the FFmpeg paragraph below):

- FFmpeg's figures are decoder time per macroblock on synthetic streams (or an
  `-skip_loop_filter all` difference), so they include its per-macroblock
  overhead and edge emulation: they are an upper bound on its kernel time.
- The deblocking comparison is not like for like: ours is a flat-plane frame
  sweep of the kernels (every line runs the whole formula, bS given); FFmpeg's
  294 ns per macroblock is on real intra content and includes its bS derivation
  and early exits.
- FFmpeg 6.1.1's H.264 qpel has SSE2/SSSE3 kernels only, no AVX2.
- The ffmpeg-stages run was at load 0.11 to 0.71 with the tool's default limit;
  the command is recorded in the file.

```go
// Predict a 16x16 block at quarter position (3, 1), then average a second
// prediction into the same block (bi-prediction, clause 8.4.2.3.1).
mc.PutLuma(dst, dstOff, dstStride, ref0, off0, refStride, 16, 16, 3, 1)
mc.AvgLuma(dst, dstOff, dstStride, ref1, off1, refStride, 16, 16, 1, 2)

// Explicit bi-weighting of two predictions into the first (8-276).
mc.WeightBi(dst, dstOff, dstStride, other, otherOff, otherStride, 16, 16, w0, w1, o0, o1, logWD)

// Deblock one vertical luma edge, then the matching chroma edge of each plane.
lf.DeblockLumaV(luma, off, stride, indexA, indexB, [4]uint8{bS0, bS1, bS2, bS3})
lf.DeblockChromaV(cb, cOff, cStride, indexACb, indexBCb, bSChroma)
lf.DeblockChromaV(cr, cOff, cStride, indexACr, indexBCr, bSChroma)
```

`indexA` and `indexB` are those of Equations 8-454 and 8-455:
`Clip3(0, 51, qPav + filterOffsetA)` and the same with `filterOffsetB`. For
chroma, `qPav` is built from the chroma QPs of the two macroblocks, QPc of
Table 8-15 (clause 8.5.8) at `qPI = Clip3(-QpBdOffsetC, 51, QPY + qPOffset)`
(Equation 8-311), where `qPOffset` is `chroma_qp_index_offset` for Cb
(8-309) and `second_chroma_qp_index_offset` for Cr (8-310): Cb and Cr can
therefore have different indexes, which is why each plane is a call of its own.

## What is guaranteed

- **The standard's integer equations.** Each kernel's result equals the
  equations of the clause above, sample for sample. The tests compare every
  position, size and parameter grid with a per-sample transcription of the
  equations written separately from the code (the portable code is the
  reference oracle, the equations are the definition).
- **Bounds are proved once per call, in Go, before any assembly runs.** The
  footprint (for luma interpolation: the block plus 2 samples before and 3
  after in each interpolated direction; for deblocking: the samples across the
  edge) and the destination block must lie inside their slices, strides must be
  usable, sizes and parameters must be in range; otherwise the call panics and
  has touched nothing. Guard-page tests (an inaccessible page right after, or
  before, a footprint-sized plane) run the assembly for every position and size
  and fail on any access outside the footprint. Arithmetic is in int64, so no
  32-bit target overflows.
- **Overlap is refused.** `PutLuma`, `AvgLuma` and `WeightBi` panic when the
  destination block and the source share memory (decided from the addresses;
  two disjoint views of one array are fine). Destination rows must not overlap
  each other (`stride >= width`).
- **Edge emulation is the caller's** until `pix` provides it: clause 8.4.2.2.1
  clamps reference coordinates (Equations 8-239, 8-240); a block whose footprint
  leaves the picture is built first.
- **Zero allocations, no goroutines**, `CGO_ENABLED=0`.

The supported luma block sizes are the seven the standard uses: 16x16, 16x8,
8x16, 8x8, 8x4, 4x8, 4x4.

## Speed

Measured on an Apple M4 Max, one core, Go benchmarks, NEON against our
portable Go. Every table below was taken at a 1-min load far above the rule's
8 (the load is given with each), so read the ratios as orders of magnitude and
re-measure on a quiet machine; raw output is in [docs/bench](docs/bench).

**Comparing with FFmpeg, per stage.** No FFmpeg `checkasm` binary is available,
so the comparison is made on decoder time.
[docs/bench/ffmpeg-stages](docs/bench/ffmpeg-stages) writes synthetic Baseline
H.264 streams (an IDR picture of I_PCM macroblocks, then P pictures of
`P_L0_16x16` macroblocks with one motion vector, no residual, no deblocking)
and times `ffmpeg -benchmark -threads 1` on them: the difference between two
picture counts, per macroblock, minus the integer-vector case, is FFmpeg's cost
of that interpolation (the chroma interpolation a fractional vector also
triggers is measured separately and removed); explicit weights are one more
case. The loop filter is `-skip_loop_filter all` on an all-intra clip. The
frame-sweep benchmarks (`BenchmarkLumaFrame`, `BenchmarkWeightFrame`,
`BenchmarkDeblockFrame`) run our kernels over every macroblock of a 1920x1088
picture, ns per macroblock, to put next to those figures: unlike the
L1-resident kernel benchmarks they include the cache and call overhead of a
decoder. FFmpeg's figures include its own per-macroblock overhead and edge
emulation on the picture border, which a kernel benchmark does not: they are an
upper bound on its kernel time. FFmpeg 6.1.1's H.264 qpel has SSE2/SSSE3
kernels only, no AVX2. The loop-filter comparison is not like for like: our
benchmark is a flat-plane sweep of the kernels (every line runs the whole
formula, bS given), while FFmpeg's figure is on real content and includes its
bS derivation and early exits. FFmpeg 6.1.1 on a Ryzen 9 7950X, run at load
below 1 with the tool's default limit: exact command and raw output in
[docs/bench/ffmpeg-stages-zen4.txt](docs/bench/ffmpeg-stages-zen4.txt).

**amd64 AVX2 `mc.PutLuma` / `AvgLuma`.** One kernel per width class (16, 8, 4),
position and put/avg, generated by `internal/genluma86`. The six-tap sum is
`(a+f) + 5*(4(c+d) - (b+e))` on sixteen-bit lanes, `Clip1Y((x+16)>>5)` is
`PMULHRSW` by 1024 plus the saturating pack, quarter positions average two
clipped terms with `PAVGB` before the single store. The centre sample is two
passes (horizontal intermediates and word pairs on the stack, then three
`PMADDWD`). No kernel reads or writes past its footprint. AMD Ryzen 9 7950X
(Zen 4), one core, ns per block (AVX2 / portable Go), L1-resident, including
the roughly 10 ns of bounds proof and dispatch of the public call (host load
0.7 to 2.7, another session; raw output in
[mc-luma-zen4-avx2.txt](docs/bench/mc-luma-zen4-avx2.txt)):

Frame sweep (every edge of every macroblock of a 1920x1088 picture, all-intra
pattern, ns per macroblock,
[lf-frame-zen4-avx2.txt](docs/bench/lf-frame-zen4-avx2.txt)): luma 128, chroma
81, together **206**; FFmpeg 6.1.1 spends **294** ns per macroblock on luma,
chroma and bS derivation in the same all-intra case (`-skip_loop_filter all`
difference; method in the bench PR's `docs/bench/ffmpeg-stages`), about 1.4
times more. Not done: AVX-512 (the vectors are sixteen lines wide, one YMM of
words; a ZMM would need two edges per call), and the Cb+Cr same-call form of
the open NEON chroma PR. The kernels are generated by `internal/genlf86`
(plain Plan 9 text, like `internal/genmc`: every instruction used exists in
`cmd/asm`, so no go-asmgen gap entry was needed).

Small blocks gain little (4x4 weighting, chroma edges): the call, the bounds
proof and the constant setup cost about as much as the arithmetic. Batching
several blocks or edges per call is the way to recover it.

## Layout

| Package | Holds |
|---|---|
| [`pix`](pix) | copy, rounding average, residual add, edge emulation (empty) |
| [`mc`](mc) | luma and chroma interpolation, weighted prediction |
| [`itx`](itx) | the 8x8 dequantise, inverse transform and add and 4x4 (AVX2, NEON, portable), the luma DC transform; chroma DC next |
| [`lf`](lf) | deblocking |
| [`ipred`](ipred) | intra prediction (empty) |
| [`cpu`](cpu) | which implementation runs on this processor (empty) |

The NEON source is generated: `go generate ./...` runs `internal/genmc`, and a
test fails when a checked-in `.s` differs from its output. `cmd/asm` lacks
`SQRSHRUN` and `SSHL` (register form); both are emitted as `WORD`s, and both
are in [go-asmgen](https://github.com/go-asmgen/asmgen)'s gap registry with
reference encodings.
