# kernels

[![ci](https://github.com/go-videodsp/kernels/actions/workflows/ci.yml/badge.svg)](https://github.com/go-videodsp/kernels/actions/workflows/ci.yml)
[![Go Reference](https://pkg.go.dev/badge/github.com/go-videodsp/kernels.svg)](https://pkg.go.dev/github.com/go-videodsp/kernels)
[![License: BSD-3-Clause](https://img.shields.io/badge/License-BSD--3--Clause-blue.svg)](LICENSE)

Video codec kernels shared by the go-avkit decoders. Every kernel computes the
integer result of the standard's equations (ITU-T H.264 (V16) (06/2026) for
now), has a portable Go implementation written from those equations, and, where
the hardware has one, an assembly implementation. H.264 is the first consumer
(go-avkit/h264); HEVC and AV1 reuse the same packages. The design, with the
profile that sets the priorities, is in
[docs/design/design.md](docs/design/design.md).

## What exists (v0.1.0)

| Kernel | Entry points | Clause |
|---|---|---|
| Luma quarter-sample interpolation, 16 positions, put and average | `mc.PutLuma`, `mc.AvgLuma` | 8.4.2.2.1, 8.4.2.3.1 |
| Explicit weighted prediction | `mc.WeightUni`, `mc.WeightBi` | 8.4.2.3.2 |
| Luma deblocking, 16 lines per call | `lf.DeblockLumaV/H` (bS 1..3), `lf.DeblockLumaIntraV/H` (bS 4) | 8.7.2.2 to 8.7.2.4 |
| Chroma deblocking, 4:2:0, 8 lines per call | `lf.DeblockChromaV/H`, `lf.DeblockChromaIntraV/H` | 8.7.2.2 to 8.7.2.4 |
| Chroma deblocking, Cb and Cr in one call, each plane with its own indexes | `lf.DeblockChromaPairV/H`, `lf.DeblockChromaPairIntraV/H` | 8.7.2.2 to 8.7.2.4 |
| Threshold tables | `lf.Alpha`, `lf.Beta`, `lf.TC0` | Tables 8-16, 8-17 |

Implementations: portable Go on every target (and with the `purego` build tag),
arm64 NEON, generated by `internal/genmc`. amd64 AVX2 is in progress; until it
lands, amd64 runs the portable code. Samples are 8 bits; 16-bit forms are not
there yet.

```go
// Predict a 16x16 block at quarter position (3, 1), then average a second
// prediction into the same block (bi-prediction, clause 8.4.2.3.1).
mc.PutLuma(dst, dstOff, dstStride, ref0, off0, refStride, 16, 16, 3, 1)
mc.AvgLuma(dst, dstOff, dstStride, ref1, off1, refStride, 16, 16, 1, 2)

// Explicit bi-weighting of two predictions into the first (8-276).
mc.WeightBi(dst, dstOff, dstStride, other, otherOff, otherStride, 16, 16, w0, w1, o0, o1, logWD)

// Deblock one vertical luma edge, then the matching chroma edge of each plane.
lf.DeblockLumaV(luma, off, stride, indexA, indexB, [4]uint8{bS0, bS1, bS2, bS3})
lf.DeblockChromaV(cb, cOff, cStride, indexACb, indexBCb, bSChroma)
lf.DeblockChromaV(cr, cOff, cStride, indexACr, indexBCr, bSChroma)
```

`indexA` and `indexB` are those of Equations 8-454 and 8-455:
`Clip3(0, 51, qPav + filterOffsetA)` and the same with `filterOffsetB`. For
chroma, `qPav` is built from the chroma QPs of the two macroblocks, QPc of
Table 8-15 (clause 8.5.8) at `qPI = Clip3(-QpBdOffsetC, 51, QPY + qPOffset)`
(Equation 8-311), where `qPOffset` is `chroma_qp_index_offset` for Cb
(8-309) and `second_chroma_qp_index_offset` for Cr (8-310): Cb and Cr can
therefore have different indexes, which is why each plane is a call of its own.

## What is guaranteed

- **The standard's integer equations.** Each kernel's result equals the
  equations of the clause above, sample for sample. The tests compare every
  position, size and parameter grid with a per-sample transcription of the
  equations written separately from the code (the portable code is the
  reference oracle, the equations are the definition).
- **Bounds are proved once per call, in Go, before any assembly runs.** The
  footprint (for luma interpolation: the block plus 2 samples before and 3
  after in each interpolated direction; for deblocking: the samples across the
  edge) and the destination block must lie inside their slices, strides must be
  usable, sizes and parameters must be in range; otherwise the call panics and
  has touched nothing. Guard-page tests (an inaccessible page right after, or
  before, a footprint-sized plane) run the assembly for every position and size
  and fail on any access outside the footprint. Arithmetic is in int64, so no
  32-bit target overflows.
- **Overlap is refused.** `PutLuma`, `AvgLuma` and `WeightBi` panic when the
  destination block and the source share memory (decided from the addresses;
  two disjoint views of one array are fine). Destination rows must not overlap
  each other (`stride >= width`).
- **Edge emulation is the caller's** until `pix` provides it: clause 8.4.2.2.1
  clamps reference coordinates (Equations 8-239, 8-240); a block whose footprint
  leaves the picture is built first.
- **Zero allocations, no goroutines**, `CGO_ENABLED=0`.

The supported luma block sizes are the seven the standard uses: 16x16, 16x8,
8x16, 8x8, 8x4, 4x8, 4x4.

## Speed

Measured on an Apple M4 Max, one core, Go benchmarks, NEON against our
portable Go. Every table below was taken at a 1-min load far above the rule's
8 (the load is given with each), so read the ratios as orders of magnitude and
re-measure on a quiet machine; raw output is in [docs/bench](docs/bench). No
comparison with FFmpeg is published yet: a checkasm binary is not available
here, and the comparison is planned on a quiet amd64 host.

`mc.PutLuma`, ns per block (NEON / portable), from
`docs/bench/mc-luma-m4max-indicative.txt` (one run, 30000 iterations; the
1-min load was 67 by `uptime` just before it; a 4x4 copy at 20.7 ns is
evidently noise):

| Block | G (copy) | b (half, H) | j (centre) | e (diagonal) |
|---|---|---|---|---|
| 16x16 | 27 / 865 | 50 / 1099 | 83 / 1619 | 61 / 1976 |
| 8x8 | 8.5 / 224 | 13.8 / 287 | 35 / 489 | 17.8 / 460 |
| 4x4 | 20.7 / 59 | 9.5 / 90 | 18.3 / 117 | 11.6 / 175 |

`mc.WeightUni` / `mc.WeightBi`, ns per block, load 26:

| Block | uni | bi |
|---|---|---|
| 16x16 | 24 / 158 | 32 / 258 |
| 8x8 | 11.6 / 48 | 14.6 / 56 |
| 4x4 | 10.4 / 12.5 | 11.1 / 15.2 |

Luma deblocking, ns per 16-line edge, flat plane (every line runs the whole
formula), load 30:

| Edge | normal (bS 1..3) | strong (bS 4) |
|---|---|---|
| vertical | 36 / 289 | 36 / 98 |
| horizontal | 25 / 126 | 15 / 76 |

Chroma deblocking, ns per 8-line edge, flat plane, load 39:

| Edge | normal | strong |
|---|---|---|
| vertical | 17 / 24 | portable (a NEON kernel tied: 13.4 / 13.2) |
| horizontal | 11 / 21 | 7.6 / 12 |

Cb and Cr in one call (`lf.DeblockChromaPair*`, each plane with its own
`indexA`, `indexB` and so its own thresholds and tC0, as
`second_chroma_qp_index_offset` can differ from `chroma_qp_index_offset`; the
two planes must not share memory). The eight lines of each plane sit side by
side in one 16-lane register, and a vertical edge packs row r of both planes
into one 8-byte row, so one 8x8 transpose yields all eight columns. Only the
strong vertical edge has such a kernel; the other three edge kinds run as two
one-plane calls inside the same API (see below). For the strong vertical edge,
ns for both planes, three runs of one call against two one-plane calls (which
run the Go code, the one-plane NEON kernel having tied it), from
`docs/bench/lf-chroma-pair-m4max-indicative.txt`; load 55 to 57 by `uptime`
around the run (`docs/bench/lf-chroma-pair-load.txt`), indicative:

| Edge | one call | two calls |
|---|---|---|
| strong vertical | 21.2, 22.7, 23.1 | 36.2, 37.2, 41.9 |

Three other two-plane kernels (normal vertical, normal horizontal, strong
horizontal) were written, measured against two one-plane calls and not kept:
a tie, a gain inside the run-to-run noise, and a loss. Those runs are not
committed, so no number for them is claimed.

Small blocks gain little (4x4 weighting, chroma edges): the call, the bounds
proof and the constant setup cost about as much as the arithmetic. Batching
several blocks or edges per call is the way to recover it.

## Layout

| Package | Holds |
|---|---|
| [`pix`](pix) | copy, rounding average, residual add, edge emulation (empty) |
| [`mc`](mc) | luma interpolation, weighted prediction; chroma interpolation next |
| [`itx`](itx) | inverse transforms and dequantisation (empty) |
| [`lf`](lf) | deblocking |
| [`ipred`](ipred) | intra prediction (empty) |
| [`cpu`](cpu) | which implementation runs on this processor (empty) |

The NEON source is generated: `go generate ./...` runs `internal/genmc`, and a
test fails when a checked-in `.s` differs from its output. `cmd/asm` lacks
`SQRSHRUN` and `SSHL` (register form); both are emitted as `WORD`s, and both
are in [go-asmgen](https://github.com/go-asmgen/asmgen)'s gap registry with
reference encodings.
